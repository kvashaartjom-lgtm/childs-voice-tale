## The two parallel pipelines

**Legacy prototype pipeline** (untouched, must stay untouched until the new
one is proven):
```
src/routes/voorbeeld.tsx (browser useEffect loop)
  -> supabase/functions/generate-character, generate-page
  -> book_jobs table
  -> Storage buckets "characters" / "pages", keyed by book_jobs.id
```
This is what actually runs today when a user completes the wizard and views
their book. It violates AD-009 (generation is browser-driven, dies if the
tab closes) — that's the whole reason the new pipeline exists. It has no
migration path yet and none should be started until the new pipeline is
proven to actually work end-to-end on a real project.

**New async pipeline** (written, unvalidated):
```
generation_jobs row (currently only created manually via SQL — nothing in
  the frontend creates one yet)
  -> pg_cron (every minute) -> pg_net -> generation-worker Edge Function
  -> claim_generation_job() (atomic claim, FOR UPDATE SKIP LOCKED)
  -> image-provider.ts (IMAGE_PROVIDER=mock by default; gemini is an
     unconfigured stub, not exercised)
  -> Storage bucket "book-pages", keyed by book_version_id
  -> book_pages.image_storage_key
```
These two pipelines are independent by design. Nothing in Phase 2b-1 reads,
writes, renames, or reuses anything from `book_jobs` or its Storage paths.

## Open questions / known drift — do not assume these are resolved

- **Whether the `vault` schema/extension exists on any given project is
  unverified.** The migration's cron job body reads
  `vault.decrypted_secrets` at call time; this was never confirmed to exist
  on staging or production. If a cron tick fails with something like
  `schema "vault" does not exist`, that's this — the fix is the same
  pattern already applied for `cron`/`net`:
  `create schema if not exists vault; create extension if not exists supabase_vault with schema vault;`
  Don't guess this in ahead of time; wait for the actual error, same as
  `pg_net`'s schema bug was handled.
- **Whether `claim_generation_job()` returns a true SQL `NULL` (not a
  row-shaped object with all-null fields) when the queue is empty is
  unverified.** The worker's `if (!job)` no-op check depends on this. It's
  standard documented plpgsql behavior and there's good reason to expect it
  works, but nothing has executed it. This is exactly what verification
  script step "0.5" checks first, before anything else, because if it's
  wrong it breaks every empty-queue tick silently rather than just one test.
- **`children` rows are created fresh on every wizard completion — this is
  intentional for now, not a bug.** `persistBookRecord()` reuses one
  `families` row per anonymous user (looked up by `owner_id`), but always
  inserts a new `children` row. A user who runs the wizard twice gets two
  `children` rows under the same family. No dedup logic exists yet; this
  was a deliberate simplification, not an oversight — revisit only if it
  becomes a real problem, not preemptively.
- **`docs/33-DEFERRED.md`** is the register of everything deliberately
  postponed with a temporary stand-in already in place and a concrete
  trigger for returning to it (Gemini paid API, Storage cleanup on cascade
  delete). Check it before assuming something is simply forgotten — it may
  already be a recorded, deliberate deferral.
